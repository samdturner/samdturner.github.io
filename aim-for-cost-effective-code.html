Aim for Cost-Effective Code

There are countless ways to engineer a feature that looks exactly the same to the user. Choosing the best implementation is the engineer's job. Should you simplify this code now or live with the complexity? Handle that edge case? Make sure it scales? Add resiliency? QA on Internet Explorer 11? Your instinct as an engineer is to value the solution that is the most scalable, the best architected, the cleanest, the most reliable, or the most performant.

But the goal of the business is not to have the code that blindly follows the most engineering best practices. The goal is to ship features that work at a high velocity. So the right way to resolve these trade-offs is to ask which option helps the business achieve this goal. That option is cost-effective code.

What is cost-effective code?

The cost of code is developer time. It is the present cost of writing the code plus the future cost of reading and changing it.

Cost-effective code is the implementation that minimizes this total cost. It ships the feature while consuming the least developer time, both now and in the future. This approach maximizes product velocity over the long run.

There are three ways to get this wrong.

Failure condition #1Building for scale you don't have yet

The first failure condition is over-investing in engineering best practices before you need them. For example, building for scalability before you have scale, or adding resiliency before anyone depends on you. The time you invest here yields no user or business value today, and it may never be needed. You are giving up today's product velocity for a future that may not arrive.

Saying no is hard because the cost is visible. Nobody wants to sit in the postmortem as the person who argued against hardening reliability. And the cost of saying yes is invisible. Nobody sees the feature you never built as the team invested more in reliability. It takes a disciplined culture to weigh both risks. Skipping the failover risks an outage, but over-preparing risks never hitting product market fit at all.

Failure condition #2Over-investing in future productivity

The second failure condition is spending too much time investing in your future productivity. This looks like:

  • Refactoring code that rarely changes
  • Migrating to a shiny new framework
  • Creating abstractions for use cases that do not exist yet

Each of these is a bet that time spent now will make you faster later. But many of these bets never pay off. The refactored module gets deleted when the feature pivots. The abstraction never gets a second use case. Meanwhile you have lowered your product velocity today, and product velocity is what buys you at-bats at finding product market fit.

Failure condition #3Under-investing in future productivity

The third failure condition is the opposite of the second. Some investments have a fast payback period, and skipping them is just as expensive. Unit tests around the code you change every week. Cleaning up the module that everyone trips over. Automating the deploy you run by hand every day. Adopting a new tool that automates a manual workflow.

This is the technical debt worth paying down. If the debt is slowing you down and cleaning it up costs less than living with it, clean it up. Otherwise you are choosing a slower team every week to save a one-time cost.

The cost-effective approach

Treat every engineering decision like a financial investment. Estimate what it costs, estimate what it pays back, and weigh how certain that payback is. That last part is the same question behind sizing your bets by your level of conviction.

Three rules follow from the failure conditions.

  1. Decline investments whose payback is too far out. The further out the payback, the more likely the product changes before it ever arrives.
  2. Decline investments when better ones are available. You can only make so many bets at once, so pursue the ones with the fastest and most certain returns first.
  3. Weigh the remaining investments against other initiatives like feature development. An hour spent on engineering investments is an hour not spent shipping, so the investment has to beat the next feature on your roadmap.

None of this is an argument against clean code, scalability, or best practices. It is an argument for buying them when they are cheap relative to what they return. up.
